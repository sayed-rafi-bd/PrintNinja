# PrintNinja V2 — Shared Templates on Turso

Status: **plan, not started**
Target release: `0.2.0`
Owner: PrintNinja

---

## 1. Why V2

V1 stores everything in a per-machine SQLite file (`src-tauri/src/db/schema.sql` via
`rusqlite`). That makes templates invisible to everyone except the person who drew them,
and it makes the REST API useless as a sharing surface — a key issued on machine A
authenticates against machine A's database, not a shared one.

Three problems, one root cause (per-device storage):

1. **No sharing.** A template lives in one install. There is no "use the invoice layout
   my colleague already built."
2. **No ownership.** `templates` has no owner column, so there is no way to express
   "you may edit this, they may only print it."
3. **No shared database.** The REST API in `src-tauri/src/api/routes.rs` reads the same
   local file, so it is a local IPC surface wearing an HTTP costume.

V2 replaces the storage engine with **Turso (libSQL)** and adds an **account + ownership +
draft/publish** model on top of it.

The loop it enables, which V1 has no way to express:

```
        ┌──────────────┐   save    ┌─────────────┐   publish   ┌──────────────┐
        │  Community   │──────────▶│ Collection  │◀───────────│   Designer   │
        │   browse     │           │  (private)  │             │   (private)  │
        └──────────────┘           └──────┬──────┘             └──────────────┘
                ▲                           │ print                   │
                └───────────────────────────┴─────────────────────────▶│
                                              everyone can use them     ▼
```

Browse is public, collection is private, and the only thing that crosses the boundary in
either direction is *save* and *publish*.

## 2. Goals

| # | Goal | Acceptance |
|---|------|------------|
| G1 | Templates are stored in a shared Turso database | New install on machine B lists templates created on machine A |
| G2 | Anyone can create / edit / delete **their own** templates | Bob cannot edit or delete Alice's template; API returns `403` |
| G3 | Everyone can **use** published templates | Bob can print Alice's published template without forking |
| G4 | Every template has a markdown README | Created templates ship with a scaffolded README; visible to all users |
| G5 | Draft → Publish workflow | Unpublished templates are invisible to other users and unprintable by them |
| G6 | Offline-capable | App is fully usable with no network; changes sync when connectivity returns |
| G7 | UI directs attention with colour | Ownership and publish state readable at a glance, without reading text |
| G8 | Anyone can **browse** the community catalogue | Bob sees every published template from every user, with owner, README and paper spec |
| G9 | Anyone can add a template to **their own collection** | Bob saves Alice's template to his collection and prints it in one action, without editing it |

### Non-goals for 2.0

- Ratings, comments, likes, or any social graph beyond "published".
- Forks with lineage tracking (clone-and-detach is fine; we just do not track ancestry yet).
- Payments, per-template licensing enforcement, or a marketplace.
- Real-time collaborative editing of the same template.
- Full-text search across template bodies (search is name + README title only in 2.0).
- **Nested or shared collections.** A collection belongs to exactly one user and holds flat
  template references. Sharing a collection is just sharing the templates it points at.
- **Custom collection names in 2.0** — one default collection per user ("My Collection").
  Named collections are a small follow-up once the table is proven in production.

## 3. Architecture

### 3.1 Storage: Turso + embedded replica

Turso is a hosted SQLite fork. The Tauri app runs on desktops and phones that are often
offline, so a pure remote client is not acceptable. We use **embedded replicas**:

```
┌───────────────────────────────────────────────┐
│  Tauri app process                            │
│                                               │
│  ┌──────────────┐        ┌──────────────────┐  │
│  │ local replica│◄──────►│ libsql::Client   │  │
│  │ (app data dir)│  sync  │  (hrana, async)  │  │
│  └──────────────┘        └────────┬─────────┘  │
└─────────────────────────────────┼─────────────┘
                                  │ HTTPS
┌─────────────────────────────────▼─────────────┐
│  Turso primary  libsql://printninja-<org>.turso.io │
└───────────────────────────────────────────────┘
```

- Local replica: `<app_data_dir>/printninja.db` (created by `libsql::Client::open("sqlite:…")`).
- Remote primary: `libsql://…turso.io`, auth token from `TAURI_TURSO_TOKEN` at build time
  and/or `TURSO_AUTH_TOKEN` in the environment, falling back to **guest/local mode** when
  absent (see §3.4).
- Sync runs on app start, on app focus, and on a 60 s timer while the window is open.

### 3.2 Replacing `rusqlite` with `libsql`

The current seam is deliberately narrow:

```rust
// src-tauri/src/db/mod.rs (V1)
pub type DbState = Arc<Mutex<Database>>;      // rusqlite::Connection per call
```

`libsql::Client` is `async` and clonable, which actually simplifies ownership compared to the
`Mutex<Connection>`. V2:

```rust
// src-tauri/src/db/mod.rs (V2)
pub type DbState = Arc<Client>;                // libsql::Client, async, Clone

impl DbState {
    pub async fn apply_schema(&self) -> Result<()> { /* idempotent DDL */ }
    pub async fn sync(&self) -> Result<()>      { /* pull then push */ }
    pub async fn sync_state(&self) -> SyncState  { /* idle | syncing | offline | error */ }
}
```

Migration impact, by area:

| Area | V1 | V2 | Notes |
|------|----|----|-------|
| `src-tauri/src/db/mod.rs` | `Arc<Mutex<Database>>` + `rusqlite::Connection` | `Arc<libsql::Client>` | every `db.lock()` call site goes |
| `src-tauri/src/commands/*.rs` | sync `fn(… State<DbState>)` | `async fn(… State<'_, DbState>)` | ~9 command modules |
| `src-tauri/src/api/routes.rs` | sync handlers | `async` handlers, already axum | minor |
| `src-tauri/src/api/auth.rs` | SHA-256 API key | moved to `users` + `sessions` (§5) | API keys stay for CI/service use |
| `src-tauri/src/lib.rs` | eager `execute_batch` | `Client::open` + `apply_schema().await` | setup hook becomes async |
| `tauri-plugin-sql` | used by the frontend | **removed** | all data access goes through our commands so auth/scoping is enforced in one place |

`rusqlite` stays in `Cargo.toml` **only** as a dev-dependency for the pure query-logic unit
tests (which run without a Turso token), so the existing 62+16+13+9+5 Rust tests keep working
offline. We add a `db/mod_test.rs` shim that gives those tests the same `*_sql()` helper
functions against an in-memory `rusqlite` connection.

New dependency: `libsql = { version = "0.9", features = ["core", "http_request", "uuid", "time"] }`.
Note: `libsql` pulls a bundled SQLite, so `rusqlite`/`libsqlite3-sys` may be deduplicated —
verify before removing.

### 3.3 Concurrency and conflicts

- Templates are single-row records edited optimistically with `updated_at`.
- `template_versions` are **append-only** — the classic no-conflict shape. Two devices
  creating a version concurrently produce two versions; the higher `version_no` wins as
  `current_version_id`, and the loser is kept in history.
- `template_readmes` are one row per template with `updated_at` — last-write-wins. Acceptable
  for prose; documented in the README editor UI ("someone else may overwrite your save").
- **No offline delete/edit conflicts are silently dropped.** On sync conflict the client
  re-reads the row, and if `updated_at` moved past the local edit's base version, the app
  surfaces a conflict toast with a diff instead of overwriting.

### 3.4 Local / guest mode

`libsql` without a remote URL is just local SQLite. If no Turso token is configured, the app
runs in **local mode**: full single-user functionality, sharing disabled, a persistent
"Sharing is not configured" notice in Settings, and every `owner_id` forced to the local
device user. This keeps forks and internal builds testable with no secrets and guarantees we
never hard-fail at startup on a missing token.

## 4. Data model

Migration `002_v2_shared_templates.sql`, additive and idempotent (`IF NOT EXISTS` throughout),
applied by `DbState::apply_schema()`.

```sql
-- ── identity ────────────────────────────────────────────────────────────────
CREATE TABLE IF NOT EXISTS users (
    id            TEXT PRIMARY KEY,            -- uuid v4
    handle        TEXT NOT NULL UNIQUE COLLATE NOCASE,  -- "alice", shown on templates
    display_name  TEXT NOT NULL DEFAULT '',
    email         TEXT UNIQUE,
    password_hash TEXT,                         -- scrypt; NULL for guest device users
    avatar_url    TEXT,
    is_guest      INTEGER NOT NULL DEFAULT 0,
    created_at    TEXT NOT NULL DEFAULT (datetime('now')),
    updated_at    TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE TABLE IF NOT EXISTS sessions (
    token      TEXT PRIMARY KEY,                -- random 32 bytes, hex
    user_id    TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    device_id  TEXT NOT NULL,
    created_at TEXT NOT NULL DEFAULT (datetime('now')),
    expires_at TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_sessions_user ON sessions(user_id);

-- ── templates ───────────────────────────────────────────────────────────────
ALTER TABLE templates ADD COLUMN owner_id    TEXT REFERENCES users(id);
ALTER TABLE templates ADD COLUMN status      TEXT NOT NULL DEFAULT 'draft'
    CHECK(status IN ('draft','published','archived'));
ALTER TABLE templates ADD COLUMN slug        TEXT UNIQUE;         -- shareable handle
ALTER TABLE templates ADD COLUMN summary     TEXT NOT NULL DEFAULT '';
ALTER TABLE templates ADD COLUMN category    TEXT;
ALTER TABLE templates ADD COLUMN visibility  TEXT NOT NULL DEFAULT 'public'
    CHECK(visibility IN ('public','unlisted'));
-- Decision D1: publish freezes a version. current_version_id keeps moving as the
-- owner edits; published_version_id is the contract every other user prints.
ALTER TABLE templates ADD COLUMN published_version_id INTEGER;
ALTER TABLE templates ADD COLUMN published_at    TEXT;
ALTER TABLE templates ADD COLUMN forked_from_id  TEXT REFERENCES templates(id);
ALTER TABLE templates ADD COLUMN use_count       INTEGER NOT NULL DEFAULT 0;

-- V1 has no owner and no published rows, so existing templates belong to whoever
-- first signs in on that device and default to draft (see §8 backfill).
CREATE INDEX IF NOT EXISTS idx_templates_owner  ON templates(owner_id);
CREATE INDEX IF NOT EXISTS idx_templates_status ON templates(status);
CREATE INDEX IF NOT EXISTS idx_templates_slug   ON templates(slug);

-- ── readme ──────────────────────────────────────────────────────────────────
CREATE TABLE IF NOT EXISTS template_readmes (
    template_id   TEXT PRIMARY KEY REFERENCES templates(id) ON DELETE CASCADE,
    markdown      TEXT NOT NULL DEFAULT '',
    updated_at    TEXT NOT NULL DEFAULT (datetime('now'))
);

-- ── usage telemetry (drives "most used" ordering) ───────────────────────────
CREATE TABLE IF NOT EXISTS template_uses (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    template_id TEXT NOT NULL REFERENCES templates(id) ON DELETE CASCADE,
    user_id     TEXT REFERENCES users(id) ON DELETE SET NULL,
    used_at     TEXT NOT NULL DEFAULT (datetime('now'))
);
CREATE INDEX IF NOT EXISTS idx_template_uses_tpl ON template_uses(template_id);

-- ── personal collections (save-for-later) ───────────────────────────────────
CREATE TABLE IF NOT EXISTS collections (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id    TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    name       TEXT NOT NULL DEFAULT 'My Collection',
    is_default INTEGER NOT NULL DEFAULT 0,
    created_at TEXT NOT NULL DEFAULT (datetime('now'))
);
CREATE UNIQUE INDEX IF NOT EXISTS idx_collections_default
    ON collections(user_id) WHERE is_default = 1;   -- partial: one default per user

CREATE TABLE IF NOT EXISTS collection_items (
    collection_id INTEGER NOT NULL REFERENCES collections(id) ON DELETE CASCADE,
    template_id   TEXT    NOT NULL REFERENCES templates(id) ON DELETE CASCADE,
    note          TEXT    NOT NULL DEFAULT '',     -- "our 80mm printer needs +2mm"
    added_at      TEXT    NOT NULL DEFAULT (datetime('now')),
    PRIMARY KEY (collection_id, template_id)
);
CREATE INDEX IF NOT EXISTS idx_collection_items_tpl ON collection_items(template_id);

-- ── abuse limits (Decision D4) ─────────────────────────────────────────────
-- Per-user, per-bucket, time-windowed. Rows are purged on write, so the table
-- stays proportional to one hour of activity rather than growing forever.
CREATE TABLE IF NOT EXISTS rate_limit_events (
    user_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    bucket  TEXT NOT NULL,                     -- 'publish' | 'fork'
    at      TEXT NOT NULL DEFAULT (datetime('now'))
);
CREATE INDEX IF NOT EXISTS idx_rate_limit ON rate_limit_events(user_id, bucket, at);

-- ── sync bookkeeping ────────────────────────────────────────────────────────
CREATE TABLE IF NOT EXISTS sync_log (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    direction  TEXT NOT NULL CHECK(direction IN ('push','pull')),
    rows       INTEGER NOT NULL DEFAULT 0,
    error      TEXT,
    at         TEXT NOT NULL DEFAULT (datetime('now'))
);
```

### Type changes worth calling out

- `templates.id` stays `INTEGER`. Renumbering to TEXT would touch every foreign key and buy
  nothing; Turso handles INTEGER PKs fine and local/global IDs stay aligned.
- `templates.current_version_id` and `template_versions.id` stay INTEGER — the append-only
  version model is the merge-friendly part of the design and is worth preserving exactly.
- `published_version_id` is a second pointer into the same append-only `template_versions`
  table, not a copy. Publishing and republishing never duplicate a version body, and the
  collection resolver is a single indexed lookup.
- Everything user-facing is TEXT/UUID because users and sessions originate on the network,
  not on one device.

### Slugs (Decision D2)

`slug` is the shareable handle behind `printninja://template/invoice-a4` and
`/v1/templates/by-slug/:slug`. Rules, applied by one `slugify()` helper:

- lowercase ASCII, `-` separators, trimmed to 60 chars, trailing `-` stripped
- derived from the name at creation, and on rename **only if** the template was never
  published — a published slug is a link other people may already hold, so it is frozen
- collisions get a `-2`, `-3`, … suffix inside the create transaction; a retry after a
  conflict re-slugs rather than erroring
- `visibility = 'unlisted'` (D2) means "reachable by link and by collection, but excluded from
  Community listings" — the escape hatch for a template that is useful but too internal for
  the public catalogue

## 4b. Save vs Fork — the distinction everything else depends on

A user collecting someone else's template needs to be able to do it two ways, and conflating
them is the mistake this section exists to prevent.

|  | **Save** (collection) | **Fork** |
|--|----------------------|----------|
| Row created | `collection_items` reference | a **new** `templates` row owned by the collector |
| Points at | the author's live template | a copy that diverges forever |
| Updates from author | **yes** — collector gets the author's fixes automatically | no, frozen at the fork point |
| Editable by collector | no | yes, it is theirs |
| Survives author deleting it | **no** — item stays but becomes `unavailable` (see below) | yes |
| Use in this action | §7.4 Collection tab | §7.3 `Fork` button |

Save is the default for "I want to use this", because it is what a user means by "add to my
collection". Fork is opt-in and only appears when the user wants to change the layout. The UI
never shows a Save button on your own template (pointing a collection item at your own
template is just "mine" and adds nothing).

**Saved templates track the author's published version (Decision D6).** A collection item
always resolves to `published_version_id`, so when the author republishes, every collector
prints the new version on their next sync. `collection_items` therefore has **no**
`pinned_version_id` column — pinning is what `fork` is for, and carrying both would make the
card need two version numbers and give users a decision they did not ask for. The version a
collector is currently getting is shown on the card (`v3`), so an upstream change is always
visible rather than silent.

**Unavailability is a first-class state.** Authors can unpublish, archive, or delete a
template that sits in someone else's collection. Those items stay in the collection (removing
them silently would lose the note) but render in a distinct `unavailable` treatment — slate
spine, muted card, and the reason spelled out ("Author unpublished this on 12 Oct") rather
than a generic dead link. A one-line recovery action, `Remove`, is the only enabled control.

**Collections sync, and so do they drift.** `collections` and `collection_items` are ordinary
rows in the replica, so a save made on a laptop appears on the phone on next sync. Because
they are per-user rows keyed on `user_id`, they never conflict across users — only across a
user's own devices, where the composite PK `(collection_id, template_id)` makes a duplicate
save idempotent rather than a conflict.

## 5. Identity and permissions

### Accounts

- **Guest device user.** On first launch the app creates a local `users` row with
  `is_guest = 1` and a device UUID. Everything works; nothing is shared.
- **Sign up / sign in.** Handle + password (optional email for recovery). `scrypt`
  (via the `scrypt` crate) with a per-user random salt, constant-time comparison, and
  generic error messages so handles cannot be enumerated.
- **Claim.** Signing in on a device that already has guest-owned templates offers to claim
  them, setting `owner_id` to the new user in a single transaction. Skipping it is fine and
  leaves them owned by the guest row.

### Permissions matrix

| Action | Owner | Other signed-in user | Guest | Anonymous HTTP |
|--------|-------|---------------------|-------|----------------|
| List templates (own) | yes | yes | yes | token required |
| List templates (public, published) | yes | yes | yes | token required |
| **Browse the catalogue** | yes | yes | yes | token required |
| View a published template's body + README | yes | yes | yes | token required |
| View a **draft** template | yes | no (404, not 403) | no | no |
| Create | yes | yes | yes | token required |
| Edit / publish / unpublish / archive | yes | no | no | no |
| Delete | yes | no | no | no |
| Fork (clone to own draft) | yes | yes | yes | token required |
| Print a published template | yes | yes | yes | token required |
| **Add to own collection** | n/a — own template is not collectible | yes | yes | token required |
| **Remove from own collection** | own item only | own item only | own item only | token required |
| **Edit a collection item's note** | own item only | own item only | own item only | token required |
| Edit/delete someone else's collection | no | no | no | no |
| Publish someone else's template on your behalf | no | no | no | no |

Saving a template is **not** an ownership transfer and grants no write access. `authorize()`
is never called with `Access::Write` on the save path — the only writes are to the caller's own
`collection_items` rows. This is the rule most likely to be got wrong, so it gets a dedicated
test (§11).

Drafts answer `404`, not `403`. A `403` confirms that a private row exists, which leaks the
fact that a colleague is mid-draft on a customer-named invoice template. Every ownership
check lives in one helper so this cannot drift per-endpoint:

```rust
// src-tauri/src/db/permissions.rs
pub enum Access { Read, Write, Owner }

/// Single source of truth. Returns `Ok(())` or the exact error to surface.
/// Drafts owned by someone else are `Err(NotFound)`, never `Err(Forbidden)`.
pub fn authorize(
    conn: &Client, template_id: i64, user: &Identity, need: Access,
) -> AppResult<Template>
```

### API keys

The existing `api_clients` table and `sha2` key hashing stay, now as a **machine** identity:
a key belongs to a `user_id`, carries scopes (`templates:read`, `templates:write`), and
resolves to the same `Identity` as a session. Service integrations and the existing
`scripts/` smoke tests keep working without changes to the header format.

## 6. Template README (markdown)

### Why it exists

A template is only shareable if people can learn how to use it: what data fields it expects,
what printer language it assumes, what the margins are. The README is that contract, and it
is a first-class column of the template rather than a comment thread.

### Default scaffold

`create_template` writes this into `template_readmes.markdown` so every template starts with
useful structure instead of a blank box:

```markdown
# {{template_name}}

<!-- Keep this short: one line on what this template is for. -->

## What it prints
<!-- e.g. A 80mm thermal receipt with the order, totals and a QR code. -->

## Data contract
<!-- The exact JSON keys this template reads. Keep in sync with Placeholders. -->

\`\`\`json
{
  "store": { "name": "", "address": "" },
  "order": { "number": "", "date": "" },
  "items": [
    { "name": "", "qty": 1, "price": 0.0, "total": 0.0 }
  ],
  "totals": { "subtotal": 0.0, "tax": 0.0, "total": 0.0 }
}
\`\`\`

## Placeholders
<!-- {{items}} loops, {{#each}} syntax, which helper generates each field. -->

## Printer requirements
- Paper: 80mm
- Language: ESC/POS
- DPI: 203
- Margins: 3mm

## Tips
- Test with `printninja://print?template=invoice-a4&test=true`

## Changelog
- v1 — initial version
```

### Editing and rendering

- **Renderer:** `react-markdown` + `remark-gfm` (tables, strikethrough, task lists, autolinks).
  Both are pure-JS, no HTML injection, and work inside the WebView and a browser build.
- **Editor:** split view on `lg`+ (source + live preview), tabbed preview/write on mobile,
  with a "Reset to default scaffold" action that warns before discarding edits.
- **Toolbar:** bold, italic, heading, link, inline code, code block, list, table, image.
  Wraps the selection in Markdown — no WYSIWYG, so what you paste is what everyone renders.
- **Preview sanitisation:** `react-markdown` does not render raw HTML by default, and we do
  not enable `rehype-raw`. Remote images are proxied through a Tauri asset protocol to avoid
  leaking the user's IP to a template author's image host.
- **Length cap:** 64 KB, validated server-side, to stop a template README becoming a payload.
- **Localisation:** README content is never translated; the *scaffolding chrome* around it
  is, so the headings arrive in the reader's language.

## 7. Frontend redesign

### 7.1 The problem

V1 has one accent (cyan) for every action. A destructive delete, a "save draft", and a
"print now" button all read as the same weight, so nothing tells the user where to look.
With ownership and publish state added, that ambiguity gets worse: five template actions
across three permission states and two workflow states.

### 7.2 Semantic colour system

Colour carries **meaning**, and each meaning has exactly one hue. New tokens in
`src/index.css`, light and dark:

| Token | Hue | Meaning | Used on |
|-------|-----|---------|---------|
| `--primary` (cyan `199 89% 48%`) | existing | **Your** action, primary CTA | Print, Save template, Sign in |
| `--success` (emerald `160 84% 39%`) | new | Published, healthy, ready | Published badge, sync OK |
| `--warning` (amber `38 92% 50%`) | new | Draft, needs attention | Draft badge, "unpublished changes" strip |
| `--info` (violet `265 83% 53%`) | new | Shared / community / saved | ★ Saved, other people's templates, Fork |
| `--destructive` (rose `0 84% 60%`) | existing | Irreversible | Delete, Revoke |
| `--muted` (slate) | existing | Read-only, secondary | Archived, unavailable, disabled, README prose |

Rule: **hue encodes who and what state; never decoration.** No new colour without a meaning
row in this table.

`--info` is violet rather than a second cyan. Cyan at `199` is the same hue as `--primary`,
and two actions that differ only in lightness do not read as different *kinds* of action —
they read as the same action in two states. Violet is the only hue left that carries no other
meaning, which is what makes it safe to reserve for "someone else's, and I have kept a
pointer to it".

### 7.3 Template cards: a status spine

Every template card gets a 4 px left border — the first thing the eye lands on:

```
┌─┃─ Invoice A4                        [ Published ]  v3
│  ┃   A4 tax invoice, 3-column totals   Alice · 142 uses
│  ┃   210 × 297 mm · A4 · HTML/CSS
│  ┃   ─────────────────────────────────────────────
│  ┃   [ Use ]  [ ★ ]  [ Fork ]  [ Readme ]
```

| Spine | Card treatment |
|-------|----------------|
| Cyan | **Yours.** Full action row: Edit, Duplicate, Delete. No ★. |
| Amber | **Yours, draft.** Amber badge, "Draft — only you can see this" subtitle, primary button reads Publish. |
| Emerald | **Theirs, published.** Primary button reads Use. No edit affordance at all. |
| Emerald + amber pip | **Theirs, published, updated since you collected it.** Same actions, plus a small amber dot and `now at v4`. |
| Slate + 60% opacity | Archived *or* collected-but-unavailable, with the reason spelled out. |

The `Use` / `Edit` / `Fork` button label changes with the spine rather than showing a
disabled Edit the user cannot have — an absent affordance costs less than a dead one. The
★ is present on every emerald card, because that is exactly the set of templates a user can
collect.

The amber pip is the visual consequence of D1 + D6: because a saved template auto-updates, a
republish by the author silently changes what the collector prints. The pip is how that
becomes visible rather than surprising — and it is the same amber as "draft", because the
meaning in both cases is *"there is a change you have not seen"*.

### 7.4 Library layout

`/templates` is a new top-level page (promoted from the Designer's embedded list) with three
tabs: **Community** (browse), **My templates** (owned), and **Collection** (saved).

```
┌──────────────────────────────────────────────────────────────────┐
│  Templates                                                       │
│  [ Community ] [ My templates ] [ ★ Collection ]                  │
│  [ Search…            ]              [Most used ▾]                │
├──────────────────────────────────────────────────────────────────┤
│  ┃ Invoice A4              │  ┃ Packing Slip 4×6                │
│  ┃ [Published] Alice       │  ┃ [Draft] you                    │
│  ┃ A4 tax invoice…  142↵   │  ┃ Packing slip for parcels…      │
│  ┃ ★ Saved                  │                                   │
└──────────────────────────────────────────────────────────────────┘
   card grid: 1 col mobile · 2 col md · 3 col xl
```

**Browse / Community** (default tab) is the answer to "what exists out there". It lists every
published template from every user and surfaces the metadata people actually need to judge
one before saving:

- name, owner handle, summary, paper size / orientation / language
- `use_count`, last-updated date
- the README rendered inline behind a **Readme** action — a shopper reads the data contract
  before deciding
- category chips (`Receipt`, `Label`, `Invoice`, `Kitchen`, `Other`)

**My templates** is the current V1 list — drafts included — with the full owner action row.

**Collection** is the saved set: one card grid, same component, with the note visible on the
card and editable inline. Prints straight from here, so the path from *"I saw it"* to *"it
printed"* is two taps.

- **Filter tabs** are the primary filter, sorted left-to-right by permission relevance.
- **Search** matches template name, summary, owner handle, category, and README headings.
  Debounced 250 ms, local first, remote when online.
- Sorting: Recently updated · Most used · A–Z. "Most used" reads `use_count`, which is
  incremented on print, not on view, so it reflects real value.
- An empty Collection tab is an onboarding opportunity, not dead space: *"Browse community
  templates"* as the primary action, plus a card explaining what saving does (you get the
  author's updates; forking detaches you).

### 7.4b Save / collect interaction

The ★ affordance is deliberately not a checkbox:

| State | Control | Colour |
|-------|---------|--------|
| Not saved | `☆ Save` outline star, tooltip "Add to my collection" | muted slate |
| Hover | fills, lifts 1 px | info (violet) |
| Saved | `★ Saved` filled, `aria-pressed="true"` | info (violet) |
| Saving (optimistic) | filled immediately, spinner replaces the label | info (violet) |
| Failed | reverts to `☆ Save`, toast with a Retry action | destructive |
| Own template | control absent entirely | — |
| Item unavailable | `★ Unavailable`, disabled | slate |

Saved is violet (`--info`), not emerald. Emerald already means *published* everywhere else in
this app (§7.2); reusing it for "saved" would overload the one hue carrying publish meaning
and make a saved template look like it had been published by its author.

Saves are **optimistic with rollback**: the star fills instantly, the `POST` fires in the
background, and a failure reverts the star and toasts. On a phone the alternative — waiting
on a network round trip — makes the control feel broken. The optimistic write is reconciled
by `useQuery`'s cache so a sync from another device cannot leave it stuck.

### 7.5 Designer changes

Three-panel on `xl`, stacked tabs on mobile:

```
┌───────────────────────────────────────────────────────────────┐
│ Invoice A4 · Draft · saved 2m ago        [Preview] [Publish]  │  header + status
├───────────────┬───────────────────────────┬───────────────────┤
│ Layers        │  Canvas / CodeMirror      │  README           │
│               │                           │                   │
│ + amber strip │                           │  markdown source  │
│   "1 unpub-   │                           │  + live preview   │
│    lished     │                           │                   │
│    change"    │                           │                   │
└───────────────┴───────────────────────────┴───────────────────┘
```

- The header carries a **state chip** with four labels, not three (D1): `Draft` amber,
  `Published` emerald, `Published · N unpublished changes` amber-dotted emerald, and
  `Archived` slate. A `Syncing` cyan chip and an `Offline` slate chip sit beside it, and the
  chip's position is fixed so it never moves as content changes.
- **Publish** on a never-published template is the emerald primary action. On an already
  published template with changes, the same button reads **Republish** in amber — republishing
  is a warning that other people's output will change, so it does not get the publish colour.
- A README tab beside the canvas so the docs are written next to the template, not in a
  separate settings screen.
- The amber strip appears whenever `current_version_id != published_version_id`, naming how
  many versions have gone out and who currently receives them.
- Mobile: tab bar `Design | Code | README | Preview`, 44 px targets, sticky action bar.

### 7.6 Nav and onboarding

- Nav becomes **Design · Templates · Print · Printers · History · Settings** (6 items; still
  a bottom bar on mobile, icons only under `sm` with labels on `md`).
- The **Templates** item carries a live count badge from the user's collection, so the set
  they chose to keep is visible from anywhere. The badge is `collection_items` count, not
  template count, and it goes slate (not amber) so it never competes with the draft warnings
  elsewhere in the UI.
- Onboarding gains one step: *"Sign in to share templates"* with an explicit **Skip for now**

  browse and a working local collection; the collection simply stays on the device.
- Settings gains a **Sync** card showing connection mode, last sync, pending changes, and a
  manual "Sync now" button — plus the Turso URL when configured.

## 8. Migration from V1

1. `apply_schema()` runs the additive DDL. `ALTER TABLE … ADD COLUMN` is guarded by a
   `PRAGMA table_info` check so re-runs are no-ops.
2. On first V2 launch, a `V1 → V2 backfill` runs in one transaction:
   - ensure a guest `users` row for this device,
   - `UPDATE templates SET owner_id = <guest>, status = 'draft', slug = <derived>`,
   - seed `template_readmes` for every migrated template with a scaffold whose "Data
     contract" section is pre-filled from the template's actual Handlebars placeholders
     (we can enumerate `{{…}}` tokens from the stored HTML).
3. Existing `template_versions`, `sample_datasets`, `print_jobs` are untouched.
4. On first successful sync, migrated rows push to Turso. Turso is seeded by this push, not
   by a SQL dump, so the migration story is identical for local and remote databases.

### Env / config

| Key | Where | Meaning |
|-----|-------|---------|
| `TURSO_URL` | `.env`, CI secret | `libsql://…turso.io` |
| `TURSO_AUTH_TOKEN` | `.env`, CI secret | primary auth token |
| `TURSO_SYNC_URL` / `TURSO_SYNC_TOKEN` | optional | read replica for long syncs |

All three optional. Absent → local mode, no crash, sharing off with an explicit UI notice.

## 9. REST API (v1 endpoints, V2 semantics)

New:

```
POST   /v1/auth/register            { handle, password, email? }      → { token, user }
POST   /v1/auth/login               { handle, password }              → { token, user }
POST   /v1/auth/logout              Bearer                            → 204
GET    /v1/auth/me                  Bearer                            → { user }
POST   /v1/auth/claim               Bearer, guest_token               → moves guest templates to user

GET    /v1/templates                ?scope=community|mine|published|collected&q=&sort=&category=
                                                                    → [TemplateSummary]
GET    /v1/templates/by-slug/{slug} → Template (published, or own if not)
POST   /v1/templates                { name, summary, page_w_mm, … }    → Template (seeds README)
GET    /v1/templates/{id}           → Template + current version + published version + README
PATCH  /v1/templates/{id}           owner only                         → Template
DELETE /v1/templates/{id}           owner only                         → 204
POST   /v1/templates/{id}/fork      → new draft owned by caller
POST   /v1/templates/{id}/publish   owner only, requires version ≥ 1  → Template
POST   /v1/templates/{id}/unpublish owner only                         → Template
POST   /v1/templates/{id}/archive   owner only                         → Template
GET    /v1/templates/{id}/readme    → { markdown, rendered? }
PUT    /v1/templates/{id}/readme    owner only, ≤64 KB                 → { updated_at }
GET    /v1/templates/{id}/versions  → [TemplateVersion]

GET    /v1/collection               → { items: [ { template, note, added_at, availability } ] }
POST   /v1/collection/{template_id} { note? }                          → 201 (idempotent)
DELETE /v1/collection/{template_id}                                   → 204
PATCH  /v1/collection/{template_id} { note }                          → { updated_at }
GET    /v1/collection/{template_id}/status                            → { saved: bool }

GET    /v1/catalog/facets           → { categories: [{ name, count }] }

GET    /v1/sync/status              → { mode, last_sync, pending, error }
POST   /v1/sync/run                 → triggers a sync, 202
```

Collection responses carry an `availability` field (`available | unpublished | archived |
deleted`) computed at read time, so the UI can render the unavailable state without a second
round trip per card. They also carry the `version_no` the collector will actually print,
resolved from `published_version_id` (Decision D6).

`POST /v1/collection/{id}` is **idempotent** on the `(collection_id, template_id)` primary
key: a repeated save updates the note and returns the existing row with `200`, not a `409`.
This matters because optimistic UI plus offline retry will double-post, and a user pressing
★ twice should not see an error.

### Rate limits (Decision D4)

`publish` and `fork` are rate-limited per user to **60/hour**, sliding window, tracked in
`rate_limit_events`. Exceeding it returns `429` with `Retry-After` in seconds and an i18n
message — never a silent no-op. Reads are not limited: browsing is the feature, and throttling
it would defeat the point of the Community tab. `fork` is limited separately from `publish` so
a user cannot exhaust one by abusing the other.

### Version compatibility (Decisions D3, D5)

`GET /v1/templates` keeps its `/v1` path; only the default `?scope` changes to `community`.
V1 clients that want their old behaviour send `?scope=mine`. This is recorded in a new
`CHANGELOG.md` with a migration note, because a silently different default for an existing
endpoint is the kind of break that is only discovered in production.

The API covers community templates as well as owned ones (D3) — it already exists, the
permission layer is shared with the in-app UI, and a `templates:read`-scoped key is how an
office server would pull the catalogue.

`/v1/openapi.json` is generated from the same table so the docs cannot drift; the
`openapi.rs` test asserts every route has an entry.

## 11. Testing strategy

**Rust (unit / integration)** — extend the existing 62+16+13+9+5 pattern:
- permission matrix: one test per row in §5, each asserting the exact error variant
- auth: scrypt round-trip, constant-time compare, session expiry, guest claim atomicity
- sync: pull-then-push ordering, `use_count` convergence, conflict detection on
  `template_versions`, offline queue drain
- scaffold: every heading present, placeholders derived correctly from stored HTML
- **publish freeze (D1):** after publish, editing creates a new `current_version_id` while
  `published_version_id` still points at the old row, and a second user printing gets the old
  body — the single test that would catch a regression here
- **auto-update (D6):** after the author republishes, a collector's resolved version moves to
  the new one, and `collection_items` still has no pin column
- **rate limit (D4):** the 60th publish in a window succeeds, the 61st is `429` with
  `Retry-After`, `fork` has its own independent bucket, and purge-on-write keeps the table
  bounded
- **slug (D2):** `slugify()` normalisation, `-2` collision suffix, and a published slug
  surviving a rename unchanged
- collections: save is idempotent; a user cannot save their own template; saving grants no
  `Access::Write` on the target; `availability` reports `unpublished` after an unpublish and
  `deleted` after a delete, with the item still present in the collection; a second user's
  collection is invisible and unmodifiable
- regression: each fixed bug gets a test that fails without the fix (V1 rule, unchanged)

**Frontend (Vitest)** — scaffold rendering, spine→action mapping, tab routing and query
params, filter/search/sort/facet logic, ★ state machine (idle/hover/saving/saved/failed/
unavailable), optimistic rollback, markdown XSS safety, mobile layout snapshots.

**E2E (Playwright)** — two browser contexts simulating two users on one machine: Alice
publishes, Bob browses and finds it, saves it to his collection, prints it from there; Alice
then unpublishes and Bob's collection item renders as unavailable. Alice's draft stays
invisible to Bob throughout.

**CI** — unchanged shape from V1: `web-check`, `rust-check`, `version-check`, `windows-build`,
`android-build`, `github-release`. Adds a `turso-check` job that boots the test suite against
a Turso replica created per-run from `TURSO_URL` + `TURSO_AUTH_TOKEN` (skipped when secrets
are absent, so forks stay green). `e2e` remains excluded from CI by the standing rule.

## 12. Risks

| Risk | Impact | Mitigation |
|------|--------|------------|
| `libsql` crate conflicts with `rusqlite`'s bundled SQLite | Build failures, CI red | B1 is the first batch and does nothing else; verify linkage before proceeding |
| Turso embedded replica conflicts corrupt local state | Data loss | Append-only versions + conflict detection (§3.3); never delete-on-conflict, always merge or surface |
| Guest→account migration is confusing | Users "lose" their templates | Explicit claim dialog, transactional, fully reversible, never automatic |
| Offline edits silently overwritten | Trust loss | LWW only for README prose and flagged in the UI; versions never overwrite |
| Per-request `Arc<Client>` vs V1's mutex | Deadlocks / contention disappear, but handlers must become `async` | Mechanical change; compiler enforces it across all 9 command modules |
| Markdown XSS via template README | Account takeover | No `rehype-raw`, no raw HTML, remote images proxied, output re-escaped |
| Collection items dangle when an author unpublishes | Users lose saved work without warning | Item persists with `availability` + date + reason; never silently dropped (§4b) |
| Users confuse Save with Fork and fork everything | Duplicate templates, upstream fixes stop flowing | ★ is the default action, Fork is a separate explicit control with a tooltip stating it detaches from the author |
| Every user's collection rows sync to every replica | Write amplification, PII in local replicas | Rows are keyed on `user_id` and filtered per query; `collection_items.note` is private to the owner and excluded from `?scope=community` payloads |

## 13. Decisions

All eight questions raised during planning are settled. Each is recorded here with its
rationale and the section that implements it, so a later change is an explicit amendment to
this document rather than a drift nobody can explain.

| # | Decision | Rationale | Implemented in |
|---|----------|-----------|----------------|
| D1 | **Publish freezes a version.** `published_version_id` is set to the current version; later edits advance `current_version_id` but not the published pointer | A reader's data contract must not change under them. Without this, a template that worked yesterday silently stops rendering correctly after an author saves | §4 schema, B6 |
| D2 | **Slug + unlisted visibility** for sharing links | Human-readable deep links are the difference between sharing a template and copy-pasting an ID; unlisted is the escape hatch for something useful but internal | §4 slugs, §9 |
| D3 | **REST API covers other people's templates**, not just owned ones | The API already exists and the permission layer is shared with the UI; a `templates:read` key is how an office server would pull the catalogue | §9 |
| D4 | **Rate limit 60/hour** on `publish` and `fork`, per user, separate buckets, reads unlimited | Turso's free tier is request-limited, and a fork-then-publish loop needs a throttle. Browsing is the product — throttling reads would defeat Community entirely | §4 schema, §9 |
| D5 | **Keep `/v1` paths**, change only the `?scope` default, document in `CHANGELOG.md` | A versioned path split costs more than it saves while the API is this young, but a silently different default must never ship undocumented | §9, B12 |
| D6 | **Saved templates auto-update** to the author's current published version; no pin column | Auto-update is the entire reason to save instead of fork. Pinning is what fork is for, and carrying both would put two version numbers on one card | §4b, B8 |
| D7 | **Build the `collections` table now, ship one flat starred list** in the 2.0 UI | The table costs nothing extra and named collections become a pure UI change later rather than a migration | §4 schema, B8, B9 |
| D8 | **Defer** "recently saved by others" and per-category landing pages | Category chips cover discovery for 2.0, and a curated featured row implies an editorial process we have not built | — |

### Consequences worth tracking

- **D1 makes "unpublished changes" a real state, not a heuristic.** A published template the
  owner has since edited is `status = 'published'` with `current_version_id !=
  published_version_id`. The Designer's amber strip (§7.5) keys off exactly that comparison,
  and the Republish action is what clears it. This is now a defined fourth state alongside
  draft / published / archived, so the state chip has four labels, not three.
- **D1 + D6 interact.** A collector always gets the newest published version, so a republish
  changes what other users print with no action from them. The version number on the card
  (§7.4b) is the only signal they get, which makes it a required field rather than a nicety.
- **D4 needs a purge job.** `rate_limit_events` grows with every publish and fork, so the
  check deletes rows outside the window in the same transaction it appends to. Without that,
  the abuse-mitigation table becomes the largest table in the database.
- **D7 keeps the API honest.** The `collections` table exists in 2.0 but the UI exposes one
  list. Endpoints therefore accept an optional `collection_id`, defaulting to the user's
  default collection, so adding named collections later is a query parameter rather than an
  API break.
- **D8 means Community has no "featured" row.** Category chips and sort are the whole of
  discovery in 2.0. If a curated row is added later it needs an endorsement model, and it
  should not be implied by existing UI.
- **D5 creates a documentation obligation.** If `/v1/templates`'s default scope changes
  without the `CHANGELOG.md` entry landing in B12, an existing integration breaks silently.
  The B12 gate includes that file for this reason.

### Change protocol

These are decisions, not preferences. Reversing one — especially D1 or D6 — invalidates data
already written by shipped versions, so it requires a migration note and an entry here, not
just a code change.
