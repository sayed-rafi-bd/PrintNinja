# PrintNinja V2 — Shared Templates

Status: **plan, not started**
Target release: `0.2.0`
Branch: `v2`

Supersedes the earlier draft of this document, which had grown into a 12-batch programme
with fork/lineage, version freezing, abuse limiting and moderation. That complexity was
self-inflicted and is gone.

---

## 1. What changes

PrintNinja V1 keeps everything in a per-machine SQLite file. Templates are invisible to
everyone but the person who drew them.

V2 moves storage to **Turso (libSQL)** so templates are shared, and adds three things on top:

1. **Accounts**, so a template has an owner.
2. **Draft → Publish**, so you decide when other people can see your work.
3. **A markdown README** on every template, so other people know how to use it.

That's the whole product change. Everything else here is plumbing to make those three work.

### The loop

```
     ┌───────────────┐    save     ┌──────────────┐   publish   ┌──────────────┐
     │   Community   │────────────▶│  Saved       │◀────────────│   Designer   │
     │   browse      │             │  (yours)     │             │   (yours)    │
     └───────────────┘             └──────┬───────┘             └──────────────┘
              ▲                            │ print
              └────────────────────────────┴──────────────────▶ anyone can use it
```

Browse is public, Saved is private, and only *save* and *publish* cross between them.

## 2. Goals

| Goal | Done when |
|------|-----------|
| Templates are shared | A new install lists templates created on another machine |
| You own your templates | You can edit/delete yours; you cannot touch anyone else's |
| Anyone can use published templates | You can print a published template that isn't yours |
| Every template has a README | New templates get a usable scaffold, not a blank box |
| Draft before publishing | Unpublished templates are invisible to everyone else |
| Anyone can browse | You can find other people's templates and save them |
| Colour directs attention | Ownership and state are readable without reading text |
| Works offline | No network means no crash; changes sync later |

## 3. Not doing

This is the anti-complexity contract. Anything here stays out until someone asks.

- **Forking / cloning / copies.** Saving a template is the only way to take one. If you want
  to change it, make your own. This removes the single largest source of complexity in the
  previous draft: no lineage, no pin-vs-track, no "did you mean to detach", no fork button.
- **Per-template collections.** One saved list, one table. No names, no folders, no notes.
- **Version freezing / `published_version_id`.** Publish is a flag. See §5.
- **Rate limiting, abuse controls, moderation queue, report button.** Open community,
  handle problems when they happen.
- **Email, password recovery, avatars.** Handle and password, nothing else.
- **Categories and facets.** Sort and search by name is enough to start.
- **Slugs and shareable links.** Templates are addressed by id.
- **Sample datasets as a published feature.**
- **Search across template bodies.** Name and summary only.
- **Ratings, comments, forks, follows, messaging, payments.**

## 4. Architecture

### 4.1 Turso with a local replica

The app runs on phones and desktops that are often offline, so a pure remote client won't
do. We use a local SQLite replica that syncs with Turso:

```
  Tauri process                        Turso
  ┌────────────────────┐   HTTPS       ┌──────────────────────┐
  │ local replica .db  │◄─────────────►│ libsql://…turso.io   │
  │ (app data dir)     │   sync        └──────────────────────┘
  └────────────────────┘
```

- Local file lives in the app data dir; all queries hit it, so reads and writes are fast and
  work offline.
- Sync runs on app start and every 60 s while open. Push local changes, pull remote ones.
- Configured with `TURSO_URL` and `TURSO_AUTH_TOKEN`.
- **No token configured → local mode.** The app runs single-user against the local file with
  a hidden implicit user, and sharing UI is not shown. This keeps development and forks
  working with no secrets. It's a handful of lines, not a feature.

### 4.2 Swapping `rusqlite` for `libsql`

Current state:

```rust
// src-tauri/src/db/mod.rs
pub type DbState = Arc<Mutex<Database>>;   // rusqlite::Connection per call
```

Target:

```rust
// src-tauri/src/db/mod.rs
pub type DbState = Arc<Client>;             // libsql::Client — async, Clone
```

`libsql::Client` is async and clonable, which is simpler than a mutex-guarded connection.
The cost is that every command becomes `async`:

| File | Change |
|------|--------|
| `db/mod.rs` | `DbState` → `Arc<Client>`, plus `apply_schema()` and `sync()` |
| `commands/*.rs` (~9 files) | sync `fn` → `async fn`; drop `db.lock()` |
| `api/routes.rs` | already axum/async |
| `lib.rs` | setup opens the client and applies the schema |
| `Cargo.toml` | add `libsql`; **remove `tauri-plugin-sql`** so all data access goes through our commands |

`rusqlite` stays as a dev-dependency so existing query tests keep running against an
in-memory database without a network. If `libsql` bundles its own SQLite, the two
`libsqlite3-sys` builds deduplicate — verify in B1 before removing anything.

### 4.3 Conflicts

Keep it boring:

- `template_versions` are **append-only**. Two devices saving at once produce two versions.
  The higher `version_no` becomes current; the other is kept in history. Nothing is lost.
- The `templates` row itself is last-write-wins on `updated_at`. A template is a name, a page
  size and a status — the risk of clobbering is low and not worth machinery.
- Nothing deletes on conflict. Ever.

## 5. Data model

Additive and idempotent. Existing tables keep working; existing rows are backfilled in §7.

```sql
-- ── who ─────────────────────────────────────────────────────────────────────
CREATE TABLE IF NOT EXISTS users (
    id            TEXT PRIMARY KEY,           -- uuid
    handle        TEXT NOT NULL UNIQUE COLLATE NOCASE,
    password_hash TEXT NOT NULL,              -- scrypt, per-user salt
    created_at    TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE TABLE IF NOT EXISTS sessions (
    token      TEXT PRIMARY KEY,               -- random 32 bytes hex
    user_id    TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    expires_at TEXT NOT NULL
);

-- ── template ownership and state ────────────────────────────────────────────
ALTER TABLE templates ADD COLUMN owner_id     TEXT REFERENCES users(id);
ALTER TABLE templates ADD COLUMN status       TEXT NOT NULL DEFAULT 'draft'
    CHECK(status IN ('draft','published'));
ALTER TABLE templates ADD COLUMN summary      TEXT NOT NULL DEFAULT '';
ALTER TABLE templates ADD COLUMN published_at TEXT;
ALTER TABLE templates ADD COLUMN use_count    INTEGER NOT NULL DEFAULT 0;

CREATE INDEX IF NOT EXISTS idx_templates_owner  ON templates(owner_id);
CREATE INDEX IF NOT EXISTS idx_templates_status ON templates(status);

-- ── the README ──────────────────────────────────────────────────────────────
CREATE TABLE IF NOT EXISTS template_readmes (
    template_id TEXT PRIMARY KEY REFERENCES templates(id) ON DELETE CASCADE,
    markdown    TEXT NOT NULL DEFAULT ''
);

-- ── your saved list ─────────────────────────────────────────────────────────
CREATE TABLE IF NOT EXISTS saved_templates (
    user_id     TEXT    NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    template_id INTEGER NOT NULL REFERENCES templates(id) ON DELETE CASCADE,
    added_at    TEXT    NOT NULL DEFAULT (datetime('now')),
    PRIMARY KEY (user_id, template_id)
);
CREATE INDEX IF NOT EXISTS idx_saved_tpl ON saved_templates(template_id);
```

That is the entire schema change. Four tables, four columns, no `sync_log`, no rate-limit
table, no slug, no collection hierarchy.

### Two things worth spelling out

**`status` is just a flag.** `draft` or `published`, nothing else. There is no
`published_version_id`, so when an owner edits a published template, everyone gets the change
on their next sync — including people already printing it. That is the accepted cost of not
tracking a frozen version, and §7 gives the owner a cheap warning so it isn't silent.

**`templates.id` stays `INTEGER`.** Renumbering to TEXT would touch every foreign key for no
benefit. Only `users.id` is a UUID, because users come from the network rather than one
device.

## 6. Who can do what

| Action | Owner | Anyone else |
|--------|-------|-------------|
| Browse published templates | yes | yes |
| Read a published template + README | yes | yes |
| Read a **draft** | yes | no |
| Create | yes | yes |
| Edit, publish, unpublish | yes | no |
| Delete | yes | no |
| Print a published template | yes | yes |
| Save to your own list | n/a (yours already) | yes |
| Unsave / see their saved list | own rows only | never visible |

Drafts answer **404, not 403**. A 403 confirms a private row exists, which would tell a
colleague someone is mid-draft on a customer-named template. One helper owns this so it can't
drift between endpoints:

```rust
// src-tauri/src/db/permissions.rs
pub fn authorize(db: &Client, id: i64, user: &Identity, need: Access) -> AppResult<Template>
```

Signing up is open: handle + password, no invite, no email. Passwords are scrypt with a
per-user salt and a constant-time compare. Sessions are opaque random tokens in a table with
an expiry.

The existing `api_clients` API keys still work for the REST API; a key just resolves to a
user id now. The LAN bind in `commands/api.rs` stays opt-in and unchanged — it is not part
of this work.

## 7. Migrating V1 data

One transaction on first V2 launch:

1. Create an implicit local user (the local-mode user from §4.1) if none exists.
2. `UPDATE templates SET owner_id = <local user>, status = 'draft'` — existing templates
   belong to whoever runs the app and start unpublished, so upgrading never exposes anyone's
   work by surprise.
3. Create a `template_readmes` row for each template, using the scaffold from §8.1 with the
   **Placeholders** section pre-filled from the `{{…}}` tokens actually present in the stored
   HTML. That part is the genuinely useful bit and it's easy.

On first sync, these rows push to Turso. Turso is seeded by that push, not by a SQL dump, so
local and remote databases take the same path.

### The unpublished-changes warning

Since `status` is only a flag, the owner needs to know their edits are about to reach other
people. In the Designer, whenever `updated_at > published_at`, show an amber strip: *"3
changes since you published — other people get these on their next sync."* No new column, no
second version pointer, and the confusion is at least named.

## 8. The README

### 8.1 Default scaffold

`create_template` writes this, so a new template starts with structure rather than a blank
box. (Outermost fence is four backticks because the scaffold itself contains a fenced block.)

````markdown
# {{template_name}}

<!-- One line: what is this template for? -->

## What it prints
<!-- e.g. An 80mm thermal receipt with items, totals and a QR code. -->

## Data contract
<!-- The JSON keys this template reads. Keep in sync with Placeholders. -->

```json
{
  "store":  { "name": "", "address": "" },
  "order":  { "number": "", "date": "" },
  "items":  [ { "name": "", "qty": 1, "price": 0.0, "total": 0.0 } ],
  "totals": { "subtotal": 0.0, "tax": 0.0, "total": 0.0 }
}
```

## Placeholders
<!-- Which {{helper}} produces which field. -->

## Printer requirements
- Paper:
- Language:
- DPI:
- Margins:

## Changelog
- v1 — initial version
````

The `{{template_name}}` token is substituted at creation. The **Placeholders** comment is
pre-filled automatically for migrated templates (§7).

### 8.2 Rendering and editing

- **Render** with `react-markdown` + `remark-gfm`. Pure JS, works in the WebView and in a
  browser. Raw HTML is *not* enabled (`rehype-raw` stays out), which is what makes a
  user-written README safe to render for every other user.
- **Edit** in a split source/preview pane on `lg`+, tabbed on mobile, with a **Reset to
  scaffold** action that warns first.
- **Toolbar** wraps the selection in Markdown: bold, heading, link, code, list, quote. No
  WYSIWYG.
- **Cap** at 64 KB, validated in Rust.

## 9. Interface

### 9.1 Colour means something

V1 uses one accent for everything, so a destructive delete and a "print now" button look
identical. V2 gives each meaning one hue and adds no colours beyond these:

| Token | Hue | Means | Used for |
|-------|-----|-------|----------|
| `--primary` | cyan `199 89% 48%` | **Your** action | Print, Save template, Sign in |
| `--success` | emerald `160 84% 39%` | Published | Published badge, Publish button |
| `--warning` | amber `38 92% 50%` | Draft, unsent changes | Draft badge, changes strip |
| `--info` | violet `265 83% 53%` | Someone else's, which you've kept | ★ Saved, other people's templates |
| `--destructive` | rose `0 84% 60%` | Irreversible | Delete, Revoke |
| `--muted` | slate | Read-only | Disabled, secondary text, README prose |

Cyan is "yours" and violet is "theirs, and you kept a copy of the pointer to it". They are
different hues on purpose — two actions differing only in lightness read as the same action
in two states.

### 9.2 Template cards

A 4 px coloured left edge is the first thing your eye lands on. Everything else follows from
that one fact:

```
┌─┃─ Invoice A4                        [ Published ]
│  ┃   A4 tax invoice, 3-column totals   Alice · 142 prints
│  ┃   210 × 297 mm · A4 · HTML/CSS
│  ┃   ─────────────────────────────────────────────
│  ┃   [ Use ]   [ ★ ]   [ Readme ]
```

| Edge | Means | Actions |
|------|-------|---------|
| Cyan | Yours | Edit, Duplicate, Delete. No ★ — it's already in your list. |
| Amber | Yours, draft | Primary button reads **Publish**; subtitle says only you can see it |
| Emerald | Someone else's, published | Primary button reads **Use**. No edit control at all. |
| Slate | Archived, or saved but since withdrawn | Read-only, with the reason stated |

An absent button beats a disabled one — showing an Edit you can't have wastes the space and
invites the click.

### 9.3 The library page

`/templates`, three tabs:

```
┌──────────────────────────────────────────────────────────────────┐
│  Templates                                                       │
│  [ Community ]  [ Mine ]  [ ★ Saved ]                            │
│  [ Search name…                    ]        [ Most used ▾ ]       │
├──────────────────────────────────────────────────────────────────┤
│  ┃ Invoice A4              │  ┃ Packing Slip 4×6                │
│  ┃ [Published] Alice       │  ┃ [Draft] you                    │
│  ┃ A4 tax invoice…  142↵   │  ┃ Packing slip for parcels…      │
│  ┃ ★ Saved                  │                                   │
└──────────────────────────────────────────────────────────────────┘
   1 col mobile · 2 col md · 3 col xl
```

- **Community** — every published template from every user, with owner handle, summary, page
  size, language and print count. This is the "what's out there" answer.
- **Mine** — yours, drafts included, with the full action row.
- **Saved** — what you kept, printable straight from here.

Search matches name and summary. Sort is Recently updated / Most used / A–Z, where "most
used" is `use_count`, incremented on print rather than on view so it reflects real use.

An empty Saved tab isn't dead space — it points at Community.

### 9.4 The star

| State | Shows |
|-------|-------|
| Not saved | `☆` outline, tooltip "Save to your list" |
| Saved | `★` filled, `aria-pressed="true"`, violet |
| Saving | Filled immediately with a spinner |
| Failed | Reverts to `☆`, toast with Retry |
| Your own template | No star at all |

Saves are **optimistic**: the star fills instantly, the request goes out in the background,
and a failure reverts it with a toast. Waiting on a round trip makes the control feel broken
on a phone.

### 9.5 Designer

Three panes on `xl`, tabs on mobile: `Design | Code | README | Preview`.

- Header shows a fixed **state chip** — `Draft` amber or `Published` emerald — so it never
  shifts position as you type.
- **Publish** is the one emerald button in the app, which is what makes it read as the
  consequential action.
- **README** is a tab next to the canvas, so docs get written beside the template rather than
  somewhere else.
- The amber changes strip from §7 sits under the header.

## 10. REST API

Small, and it keeps the existing `/v1` paths. New:

```
POST   /v1/auth/register      { handle, password }        → { token, user }
POST   /v1/auth/login         { handle, password }        → { token, user }
POST   /v1/auth/logout        Bearer                      → 204
GET    /v1/auth/me            Bearer                      → { user }

GET    /v1/templates          ?scope=community|mine|saved&q=&sort=  → [TemplateSummary]
POST   /v1/templates          { name, summary, … }        → Template (seeds README)
GET    /v1/templates/{id}     → Template + version + README
PATCH  /v1/templates/{id}     owner only                  → Template
DELETE /v1/templates/{id}     owner only                  → 204
POST   /v1/templates/{id}/publish    owner only           → Template
POST   /v1/templates/{id}/unpublish  owner only           → Template
GET    /v1/templates/{id}/readme     → { markdown }
PUT    /v1/templates/{id}/readme     owner only, ≤64 KB    → { updated_at }

GET    /v1/saved                    → [TemplateSummary]
POST   /v1/saved/{template_id}      → 201
DELETE /v1/saved/{template_id}      → 204

GET    /v1/sync/status              → { mode, last_sync, pending }
POST   /v1/sync/run                 → 202
```

`POST /v1/saved/{id}` is idempotent — a repeat updates and returns `200`, because optimistic
UI plus retry will double-post and pressing ★ twice shouldn't produce an error.

One behavioural change to an existing endpoint: `GET /v1/templates` now defaults to
`?scope=community`. Anything wanting the old behaviour sends `?scope=mine`. That's a
`CHANGELOG.md` line in B6.

## 12. Tests

**Rust** — keep the existing split (62+16+13+9+5) and add per batch:
- the §6 matrix, one test per row, asserting the exact error variant
- drafts return `404`, never `403`
- save is idempotent and grants no `Access::Write` on the target
- migrating a V1 database assigns ownership and seeds READMEs in one transaction
- publishing makes a template visible to a second user; unpublishing hides it again
- README cap rejects oversize; a `<script>` payload renders as text

**Vitest** — star states including optimistic rollback, spine → actions mapping, tab routing,
search and sort, markdown XSS safety, layout snapshots at 375/768/1280.

**Playwright** — two sessions: Alice publishes, Bob finds it in Community, saves it and
prints from his Saved tab. Alice's draft is never visible to Bob.

**CI** — unchanged job shape (`web-check`, `rust-check`, `version-check`, `windows-build`,
`android-build`, `github-release`). `e2e` stays excluded, per the standing rule.

## 13. Still needs an answer

Three, and none of them are design work.

1. **The Turso database doesn't exist yet.** Someone has to create the org and the database and
   hand over a token for `TURSO_URL` / `TURSO_AUTH_TOKEN`. B1 connects to it, so it blocks
   B1. Also worth settling while you're there: one database for dev and prod, or two? Two is
   safer — one means local development can write to production templates — but it doubles the
   CI setup.
2. **Does `v2` build in CI?** The workflow currently runs on `main` only, so pushes to this
   branch are invisible until a PR opens. B1 rewrites every Rust command module, and CI is the
   cheapest place to catch that. Probably worth adding `v2` to the trigger branches before
   starting.
3. **Should deleting a template you've shared be reversible?** `DELETE` cascades, so it would
   vanish from everyone who saved it. Given everything in your list is public and shared, you
   may want delete to be soft with a purge window. Cheap to add now, annoying after 2.0 ships.
